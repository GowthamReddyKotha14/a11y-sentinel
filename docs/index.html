      System design

      How it works

      A crawler feeds a real browser; results flow into a scan history; a diff decides whether a change can ship. Separately, a fix agent proposes patches and a verifier decides whether to trust them.

      🕷️

      Crawl

      Stays on one site, obeys robots.txt, waits between pages.

      crawler.py
      🔬

      Scan

      Headless Chromium runs axe-core against WCAG 2.1 A/AA after CSS and JS load.

      scanner.py
      🗄️

      Store & diff

      Every scan saved in DuckDB; each issue fingerprinted to find new, fixed, and open.

      store.py, diff.py
      🚦

      Engineering decisions

      The trade-offs behind it

      The interesting part of this project isn't calling a scanner. It's deciding what to trust, what to block, and what to leave to a person.

      01

      Never trust the fix, verify it

      A model can "fix" a missing alt by deleting the image. The checker goes quiet and the content is gone. Every fix must keep the element's tag and text, reduce the failure, and break nothing else.

      02

      Gate on regressions, not the backlog

      A gate that fails on 300 old issues gets switched off in a week. Blocking only new serious issues is enforceable from day one.

      03

      Fingerprints that survive copy edits

      Identity is page + rule + selector, not the element's HTML, so a text change doesn't look like a new issue. A restructure shows as fixed + new: noisy, but never silent.

      04

      Rules first, LLM second

      Missing language tags and unlabeled fields are mechanical: fixed by rules instantly, for free. The LLM handles what needs judgement.

      05

      Verified isn't the same as correct

      The verifier proves an image has alt text, not that it describes the picture. Those fixes are flagged for human review.

      06

      Held to its own standard

      The test suite scans the tool's own report and fails on any violation. This page passes the same check.
